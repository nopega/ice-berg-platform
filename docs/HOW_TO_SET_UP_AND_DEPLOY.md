# How to set up and deploy the platform

> *"Guidelines on how to set up and deploy this architecture."* — Deliverable 2

Three phases, in an order that is a dependency chain, not a preference:

```
1. script/set_up_cluster/        00 → 10   the AWS ground the platform stands on
2. script/set_up_component/      01 → 07   the platform itself
3. script/set_up_public_access/            hostnames, TLS, the shared ALB — LAST
```

Public access is last because an Ingress needs a Service to point at, and the
ACM certificate must cover every hostname before any of them resolve. Running
it earlier produces targets that are unhealthy for reasons that look like bugs.

**Every script is a command with modes.** No argument deploys; `verify` checks;
`uninstall`/`delete` reverses where that is safe. `verify` deliberately checks
the thing most likely to be *quietly* wrong, not the thing easiest to check —
a pod being `Running` proves very little. Run it after every step; each one
prints what a failure means and which script fixes it.

**Secrets never pass through your hands.** Values are generated by
`openssl rand` or typed into hidden `read -rs` prompts, stored in AWS Secrets
Manager, and written into Kubernetes Secrets via stdin. Nothing lands in git,
shell history, or this document. Re-running any secrets script is safe — they
read the stored value back rather than generating a new one.

What each choice below costs and why it was made is not repeated here — this
is the *how*; `ARCHITECTURE.md` is the *why*; per-folder READMEs carry the
detail.

## Prerequisites

| Tool | Why |
|---|---|
| `aws` CLI v2 | everything below |
| `eksctl` | creates the cluster from `eks-cluster.yaml` |
| `kubectl` | see `02_eks_cluster_prod/INSTALL_KUBECTL.md` |

| `docker` | building the Spark image (phase 2, step 06) |

you control (this build uses Cloudflare), and a GitHub account for the two
runtime repos.

```bash
cd script/set_up_cluster/00_aws_cli_setup
./00_setup_aws_cli.sh          # configures credentials + region ap-southeast-1
```

## Phase 1 — `set_up_cluster/`: the ground

Run the numbered folders in order. The numbering *is* the dependency graph;
two orderings matter enough to explain and are marked below.

| # | Run | Creates |
|---|---|---|
| 01 | `01_create_s3_buckets_prod.sh` | `data-store-prod-warehouse` + `-logs`, versioning, **lifecycle rules from the JSON files beside it** |
| 02 | `02_create_eks_cluster_prod.sh` | EKS 1.34 from `eks-cluster.yaml`: VPC across 2 AZs, `ng-ondemand` 5/5/7, `ng-spot` 0/0/4, addons, single NAT. **~20 minutes** |
| 03 | `03_create_irsa_role_prod.sh` | the base IRSA role + OIDC provider wiring |
| 04 | `04_01_create_rds_prod.sh` → `04_02_create_databases_prod.sh` | RDS Postgres **17** (pinned — RDS defaults to 18, which Airflow does not support), private subnets only; then the `iceberg_catalog` and `airflow` databases |
| 05 | `05_create_storageclass_prod.sh` | the default **gp3** StorageClass. EKS ships the CSI driver but no class — without this every PVC stays `Pending` forever with a message that reads like a scheduling problem |
| 06 | `00_…grafana_secret` → `01_install_monitoring` → `02_…cloudwatch_irsa` | kube-prometheus-stack: Prometheus 3.13.2, Grafana 13.1.3, Alertmanager |
| 07 | `06_create_vpc_endpoints_prod.sh` | the **S3 gateway endpoint** — the largest cost decision in the platform, see `COST.md` |
| 08 | `01_create_irsa_prod.sh` → `02_install_controller_prod.sh` | AWS Load Balancer Controller. Installs the controller only; **no ALB exists until phase 3 applies an Ingress** |
| 09 | `00_…irsa_and_tags` → `01_install_cluster_autoscaler_prod.sh` | Cluster Autoscaler, version-locked to the cluster's 1.34. Step 00 writes the **ASG node-template tags** without which scaling from zero silently never happens |
| 10 | `01_install_metrics_server_prod.sh` | metrics-server as an EKS managed addon. EKS does not ship it, and without it every HPA shows `<unknown>` and never scales — this was learned live, see `AUTOSCALING.md` |

**Why monitoring is 06, before the LB controller and autoscaler.** The
Prometheus Operator installs the `ServiceMonitor` and `PrometheusRule` CRDs. A
chart cannot create objects of a kind that does not exist, and steps 08 and 09
both ship ServiceMonitor templates. Installing monitoring later would mean
going back and upgrading releases already installed. Its own only hard
prerequisite is 05 — Prometheus and Grafana need a PVC that can bind.

**Checkpoint before phase 2:**

```bash
kubectl get nodes -L workload          # 5 Ready, all workload=critical
kubectl get storageclass               # gp3 (default)
kubectl get pods -n monitoring         # all Running
cd 09_cluster_autoscaler_prod && ./01_install_cluster_autoscaler_prod.sh status
```

## Phase 2 — `set_up_component/`: the platform

Same rule: numbered folders, in order. Inside each folder the scripts are
numbered too — the usual shape is *IAM/IRSA → secrets → helm install → verify*.

### 01 — Polaris, the Iceberg REST catalog

```bash
cd set_up_component/01_iceberg_catalog_and_polaris_prod
./00_create_polaris_storage_role_prod.sh   # the role Polaris assumes to vend S3 creds
./01_create_namespace_and_sa_prod.sh
./02_create_persistence_secret_prod.sh     # RDS password -> k8s Secret
./03_bootstrap_polaris_realm_prod.sh
./04_install_polaris_prod.sh               # vendored chart; persistence=relational-jdbc
./05_create_catalog_prod.sh                # catalog `data_platform`
./06_create_team_roles_prod.sh             # etl / team_a / team_b / finance_viewer
./07_create_dg_namespaces_prod.sh          # medallion.category.domain tree
```

The one setting that must never be defaulted: the chart ships
`persistence.type: in-memory`, which loses **every table pointer** on a pod
restart. `04_install` sets `relational-jdbc` against RDS. Step 07's namespace
tree is also the S3 prefix layout and the retention policy key — the path *is*
the policy (`S3_DATA_TIER.md`).

### 02 — Trino, the only door to the data

```bash
cd ../02_trino_prod
./01_create_trino_secret_prod.sh           # Polaris connection
./02_create_trino_auth_secrets_prod.sh     # bcrypt password file: etl_setup + team_b_powerbi
./03_install_trino_prod.sh                 # coordinator + 2 workers, HPA 2-5
```

Auth, file-based access rules (BI account reads gold only), and resource
groups (Team A cannot starve Team B) all live in the vendored
`chart/trino/values.yaml`, every deviation marked `CHANGED (data-platform)`.

### 03 — cloudflared *(skip)*

Historically this WAS the way in: during the original build, before the ALB
existed, every UI was reached through a Cloudflare Tunnel. The ALB superseded
it — real hostnames, a real certificate, and no 100 MB request-body cap that
broke `docker push` to Harbor. The folder stays only because the same tunnel
fronts a hostname outside this platform.

**A fresh build does not need it, because nothing before phase 3 needs a web
entry point.** Every setup script talks to the API server directly, and
anything you want to *look at* before the ALB exists is a port-forward away:

```bash
kubectl port-forward -n airflow    svc/airflow-api-server              8080:8080
kubectl port-forward -n monitoring svc/kube-prometheus-stack-grafana   3000:80
kubectl port-forward -n data-platform svc/trino                        8081:8080
```

Phase 3 replaces these with permanent URLs.

### 04 — Airflow

```bash
cd ../04_airflow_prod
./00_create_airflow_irsa_prod.sh           # per-component ServiceAccounts; workers can
                                           # create SparkApplications, NOT pods
./01_create_airflow_secrets_prod.sh        # metadata DB, webserver key, git-sync
./02_install_airflow_prod.sh               # 3.2.2, KubernetesExecutor, DAGs by git-sync
./03_create_airflow_admin_prod.sh
./04_create_smtp_secret_prod.sh            # Gmail app password -> smtp_default connection
```

DAGs come from `github.com/nopega/airflow_dag` by git-sync — pushing to that
repo is deploying. The local `dags/` folder is a mirror; nothing in this
repository is read by the scheduler.

### 05 — Harbor, the private registry

```bash
cd ../05_harbor_prod
./00_create_harbor_bucket_and_iam_prod.sh  # registry bucket + scoped IAM key (not IRSA —
                                           # Harbor's bundled distribution can't; see README)
./01_create_harbor_secrets_prod.sh
./02_install_harbor_prod.sh                # 2.15.1, image layers in S3, Trivy scan on push
```

Harbor must exist **before** Spark: step 06 pushes the pipeline image into it.

### 06 — Spark: operator, image, credentials

```bash
cd ../06_spark_prod
./00_create_spark_irsa_prod.sh             # event-log write; also creates spark-events/ marker
./01_create_namespace_and_sa_prod.sh       # RBAC — asserts airflow CANNOT create pods
./02_install_spark_operator_prod.sh        # Kubeflow Spark Operator 2.5.0
./03_build_and_push_image_prod.sh          # Spark 4.0.1 + Iceberg 1.10.2 -> Harbor
                                           # (--platform linux/amd64 is not optional)
./04_create_image_pull_secret_prod.sh
./05_create_polaris_credential_prod.sh     # the `etl` principal the drivers authenticate as
kubectl apply -f 06_smoke_test.yaml        # end-to-end proof, no Airflow involved
```

The smoke test exercises the whole chain — Harbor pull, IRSA, Polaris
credential vending, 3-level namespace, Iceberg write, read-back — before any
real pipeline exists. If it passes, every later failure is in the pipeline, not
the platform. (`07_deploy_history_server_prod.sh` is written and optional —
not deployed in this build.)

### 07 — Argo CD, so nothing above drifts

```bash
cd ../07_argocd_prod
./01_install_argocd_prod.sh
kubectl apply -f applications/root.yaml    # app-of-apps: 8 Applications in sync waves
```

From here git is the desired state for every Helm release installed above.
The root Application reads `applications/` from the platform repo — **it finds
nothing until the tree is pushed to GitHub**.

**Checkpoint before phase 3** — run the DAG once, end to end:

```bash
kubectl exec -n airflow deploy/airflow-scheduler -c scheduler -- \
  airflow dags trigger nyc_taxi_medallion -c '{"date": "2024-01-15"}'
```

Bronze → silver → gold green proves everything phase 3 will publish.
(`HOW_TO_PERFORM_ETL.md` for what this runs and how to read a failure.)

## Phase 3 — `set_up_public_access/`: the way in

```bash
cd script/set_up_public_access
./01_request_acm_certificate_prod.sh   # request cert (6 names) -> prints DNS validation
                                       # rows -> creates them via the Cloudflare API ->
                                       # polls until ISSUED. One command, it waits.
./02_apply_public_ingress_prod.sh      # applies ingress-public.yaml -> ONE shared ALB
                                       # (group.name) -> creates DNS records -> curls
                                       # every hostname and prints a status table
```

Two inputs it will ask for: your **public IP** (saved to a gitignored
`.inbound-cidrs` file — there is deliberately no default; without it the ALB
would be open to the world) and a **Cloudflare API token** via hidden prompt.
The script also allowlists the cluster's NAT gateway IP itself — without that,
nodes cannot pull from `harbor.nopega.net` and every pod start times out.

Three facts that save an afternoon here, earned the slow way
(`set_up_public_access/README.md` has the full stories):

- **ACM certificates are immutable.** Adding a hostname later means a new
  certificate and re-validation, not an edit. `verify` prints the names the
  live certificate actually carries — trust that output, not any list in a doc.
- **Never delete the ACM validation CNAMEs** from DNS. Automatic renewal
  re-checks them.
- **A new hostname can look broken for up to 30 minutes** if anything queried
  it before its record existed — that resolver cached NXDOMAIN. Prove the
  stack with `curl --resolve` and wait the cache out; do not redeploy.

Done when:

```bash
./02_apply_public_ingress_prod.sh verify
curl -s https://trino.nopega.net/v1/info | jq .nodeVersion
```

trino · airflow · harbor · grafana · argocd · prometheus — all answering over
HTTPS through one ALB. Users connect per `HOW_USERS_CONNECT_AND_QUERY.md`.

## After it is up

| Task | Where |
|---|---|
| Pause everything without losing state | `script/scale/scale_down.sh` — node groups to 0, RDS stopped; `scale_up.sh` reverses. Helm releases and databases survive |
| Tear down completely | phase 3 → 2 → 1 in reverse; the cluster itself via `02_eks_cluster_prod/99_delete_eks_cluster_prod.sh` |
| Is it healthy | `HOW_TO_MONITOR_THE_PLATFORM.md` |
| Something is stuck | the owning folder's `verify`, then its README — each documents its own failure modes next to the step that causes them |
