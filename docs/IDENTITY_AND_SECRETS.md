# Identity and secrets

Every AWS identity and every credential in the platform, in one place. The
individual reasoning lives in each script; this is the map.

Two rules hold everywhere, and the exceptions to each are listed explicitly
rather than left to be discovered:

1. **A pod gets AWS access through IRSA, never a static key.**
2. **A credential is generated by a script, stored in AWS Secrets Manager, and
   piped into a Kubernetes Secret.** It is never a command-line argument, never
   in shell history, never in this repository.

## IAM roles (IRSA)

Eight roles. Each is assumable by exactly one ServiceAccount in one namespace —
the trust policy names `system:serviceaccount:<ns>:<sa>`, so a role cannot be
picked up by a pod that merely happens to run nearby.

| Role | Used by | Can do | Created in |
|---|---|---|---|
| `data-platform-prod-irsa-role` | `data-platform-workload` SA | the general workload role: read/write the warehouse prefix | `set_up_cluster/03_irsa_role_prod/` |
| `data-platform-prod-spark-irsa-role` | `spark` SA in `spark` | write Spark **event logs** to `s3://data-store-prod-logs/spark-events`, plus legacy warehouse grants | `06_spark_prod/00_create_spark_irsa_prod.sh` |
| `data-platform-prod-airflow-irsa-role` | Airflow SAs in `airflow` | read/write `s3://data-store-prod-logs/airflow/*` for remote task logs | `04_airflow_prod/00_create_airflow_irsa_prod.sh` |
| `data-platform-prod-polaris-storage-role` | assumed **by Polaris**, not by a pod | read/write the whole warehouse bucket — this is the role whose credentials Polaris vends | `01_iceberg_.../00_create_polaris_storage_role_prod.sh` |
| `data-platform-prod-polaris-assume-storage-role` | Polaris pod SA | one permission: `sts:AssumeRole` on the role above | same script |
| `data-platform-prod-aws-lbc-role` | `aws-load-balancer-controller` SA | create and manage ALBs, target groups, security group rules | `08_load_balancer_controller_prod/` |
| `data-platform-prod-cluster-autoscaler-role` | `cluster-autoscaler` SA in `kube-system` | describe all ASGs; **modify only** those tagged `k8s.io/cluster-autoscaler/data-platform-prod=owned` | `09_cluster_autoscaler_prod/00_create_autoscaler_irsa_and_tags_prod.sh` |
| `data-platform-prod-grafana-cloudwatch-role` | `kube-prometheus-stack-grafana` SA | read-only CloudWatch metrics and Cost Explorer | `06_monitoring_prod/02_create_grafana_cloudwatch_irsa_prod.sh` |

### Why Polaris has two roles

This is the only two-role arrangement here and it is the most important one to
understand, because it is what makes catalog permissions real rather than
decorative.

```
Spark pod
  └── authenticates to Polaris as the `etl` principal (OAuth2 client credential)
        └── Polaris checks that principal's catalog privileges
              └── Polaris assumes data-platform-prod-polaris-storage-role
                    └── returns S3 credentials scoped to the allowed prefixes
                          └── Spark writes the table
```

The Polaris pod itself can do almost nothing: its role holds a single
`sts:AssumeRole`. The role with real S3 power is only ever assumed on behalf of
a caller Polaris has already authorised.

Consequences worth knowing:

- **Spark's own IRSA role is not what writes table data.** It covers the event
  log only. When a Spark job cannot write a *table*, the policy to read is the
  storage role's, not Spark's — a diagnosis path that is not the obvious one.
- **Which principal Spark presents decides what it can touch.** It used to
  present the Polaris root credential, which made the vending step vacuous.
  `06_spark_prod/05_create_polaris_credential_prod.sh` switched it to `etl` and
  refuses to install if it detects the root client ID.

### Where IRSA is not used, and why

| Component | Uses | Reason |
|---|---|---|
| **Harbor → S3** | IAM access key in a Secret | Harbor 2.15.1 bundles distribution 2.8.x, whose S3 driver hardcodes a credential chain with no web-identity provider. The projected token is mounted and ignored — this is a property of the upstream image, not a choice. Key scoped to one bucket. Revisit when Harbor ships distribution 3.x |
| **Cloudflare DNS** | API token | not AWS. Scoped to DNS edits in one zone |
| **Gmail SMTP** | app password | not AWS. Revocable on its own, requires 2-Step Verification on the account |

| Secret | Consumed by | Notes |
|---|---|---|
| `data-platform-prod-trino-powerbi-password` | BI clients | the only credential that leaves the cluster; gold-read-only |

Trino refuses anything below 8 with
`HashedPasswordException: Minimum cost of BCrypt password must be 8`, which
surfaces as an HTTP 500 rather than as an authentication error.

## How a secret reaches a pod

```bash
PASSWORD="$(openssl rand -base64 48 | tr -dc 'A-Za-z0-9' | cut -c1-32)"
aws secretsmanager create-secret --name "$SM_NAME" --secret-string "$PASSWORD"

printf '%s' "$PASSWORD" \
  | kubectl create secret generic "$K8S_SECRET" -n "$NS" \
      --from-file=key=/dev/stdin --dry-run=client -o yaml \
  | kubectl apply -f -
```

The pipe is the point. `--from-literal=key=$PASSWORD` would put the value in
the process list, where any user on the machine can read it with `ps`, and in
shell history. Alphanumeric-only avoids escaping surprises in the clients that
later paste these into connection strings.

Two secrets are typed by a human instead — the Gmail app password and the
Cloudflare token, neither of which can be generated locally. Both are read with
`read -rs`, so they are never echoed and never become an argument.

## Rotating

| Secret | Procedure | Impact |
|---|---|---|
| Trino passwords | delete from Secrets Manager, re-run `02_create_trino_auth_secrets_prod.sh`, restart the coordinator | brief; auth happens on the coordinator only |
| Grafana admin | `00_create_grafana_secret_prod.sh rotate`, restart Grafana | seconds |
| Harbor robot | `04_create_image_pull_secret_prod.sh rotate` | image pulls fail between delete and create |
| Airflow Fernet key | **do not rotate casually** | every stored connection becomes unreadable |
| Trino shared secret | **not while serving** | workers with the old value are rejected |
| Gmail app password | revoke in Google, `04_create_smtp_secret_prod.sh rotate`, `kubectl rollout restart deploy -n airflow` | alerts stop until the restart — the env var is read at pod start |

Anything read as an environment variable needs a pod restart, not just a Secret
update. That catches people: the Secret shows the new value and the pod keeps
using the old one until it is recreated.

## What is still weak

| Gap | Why it matters |
|---|---|
| Kubernetes Secrets are base64 in etcd | anything with `get secrets` in a namespace reads them in full. EKS envelope encryption with a KMS key plus a restrictive Role are the two fixes; neither is applied |
| No automatic rotation | every rotation above is manual. Secrets Manager can rotate on a schedule with a Lambda, which is worth it for the RDS password and little else here |
| No Vault | dynamic per-pod database credentials with individual audit would replace most of this table. Deferred deliberately — see `STACK_SUMMARY.md` → "Secrets: what is implemented now, and the Vault upgrade path" |
| Harbor's S3 key is long-lived | the one static AWS credential in the platform, and it cannot be removed until upstream Harbor supports web identity |
