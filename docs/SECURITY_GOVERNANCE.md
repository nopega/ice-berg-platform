# Security and governance

What is enforced today, what is deliberately not, and where each control lives
in the repository. Anything listed as built can be checked with the command
next to it.

An earlier version of this document claimed NetworkPolicy, column masking and
query audit logging that do not exist, while listing IRSA and TLS as future
work when both were already in use. The corrections are kept visible rather
than quietly rewritten — a security document that overstates is worse than one
that admits a gap, because the gap it hides is the one nobody goes looking for.

## Identity: who can reach what

### Human and BI access to data

Everything arrives through Trino, over HTTPS, with a password.

| Control | Where | Verify |
|---|---|---|
| **Password authentication** | `02_trino_prod/chart/trino/values.yaml` → `server.config.authenticationType: PASSWORD`; bcrypt cost 10 password file generated by `02_create_trino_auth_secrets_prod.sh` | `curl -sI https://trino.nopega.net/v1/statement` → 401 |
| **File-based authorization** | same file → `accessControl`, mounted as a ConfigMap, re-read every 60s | `SELECT` from bronze as `team_b_powerbi` → Access Denied |
| **TLS** | ACM certificate on the shared ALB, 6 hostnames | `openssl s_client -connect trino.nopega.net:443` → issuer Amazon |
| **Source IP allowlist** | `alb.ingress.kubernetes.io/inbound-cidrs` on every Ingress | `set_up_public_access/.inbound-cidrs` |

Two accounts exist, and the split is the point:

| Account | Can read | Can write | Notes |
|---|---|---|---|
| `team_b_powerbi` | `gold.*` only | nothing | the credential that leaves the cluster |
| `etl_setup` | everything | everything | terminal use only |

Gold is the only layer with a contract. Bronze is a verbatim copy of whatever
the publisher sent, and silver's shape changes whenever a cleaning rule
changes — so restricting the BI account protects the dashboard as much as it
protects the data.

**What this authorization does NOT do.** Access is granted per schema. There is
no column masking and no row filtering. A user who can read a gold table reads
all of it. Trino supports both through the same rules file
(`columns` with a `mask`, and `filter` expressions per table), and adding them
is a change to one ConfigMap — but they are not configured, and no data in this
platform currently needs them.

### Workload access to AWS

Eight IAM roles, assumed through IRSA. No pod holds a static AWS key, with one
documented exception.

Full inventory, including what each role can and cannot do:
**`IDENTITY_AND_SECRETS.md`**.

The exception is Harbor: it authenticates to S3 with an IAM access key because
Harbor 2.15.1 bundles distribution 2.8.x, whose S3 driver hardcodes a
credential chain containing no web-identity provider. The projected token is
mounted and ignored. The key is scoped to one bucket and stored in Secrets
Manager. Reasoning and the upstream source are quoted in
`05_harbor_prod/00_create_harbor_bucket_and_iam_prod.sh`.

### Catalog-level access

Spark does not reach S3 with its own credentials for table data. It
authenticates to Polaris as the `etl` principal, and Polaris vends short-lived
S3 credentials scoped to that principal's catalog privileges
(`CATALOG_MANAGE_CONTENT`).

This is the control that actually binds. Switching Spark from the Polaris root
credential to `etl` — `06_spark_prod/05_create_polaris_credential_prod.sh` —
changed what a compromised Spark pod could touch from "the whole catalog" to
"what the ETL principal is allowed to write".

It also means the diagnosis path is not the obvious one: when Spark cannot
write a table, the policy to read is the storage role's
(`data-platform-prod-polaris-storage-role`), not Spark's own IRSA role.

## Secrets

Seventeen credentials, all generated by `openssl rand` inside a setup script,
stored in AWS Secrets Manager, and delivered into the cluster by piping through
`kubectl apply --dry-run=client -o yaml`.

No credential is ever a command-line argument — so none appears in shell
history or in a process list — and none is in this repository. The Gmail app
password and the Cloudflare API token are prompted for with `read -rs`, which
is why they are never echoed either.

Inventory and rotation procedure per secret: **`IDENTITY_AND_SECRETS.md`**.

What a Kubernetes Secret still is, honestly: base64 in etcd, readable in full
by anything holding `get secrets` in that namespace. EKS envelope encryption
with a KMS key and a Role that withholds `get secrets` from everything except
the workload ServiceAccount are the two fixes, and neither is applied.

## What is deliberately not exposed

| Component | Reachable how | Why not public |
|---|---|---|
| Polaris management API | `kubectl port-forward` | creates catalogs, principals and grants — an admin API with that reach does not belong on a hostname |
| Alertmanager | port-forward | no authentication of its own |
| RDS | in-VPC only | no public endpoint, ever |

Public hostnames and what protects each one: `set_up_public_access/README.md`.

Two of them carry a trade-off worth naming rather than burying. **Prometheus**
has no login at all; the allowlist is the only control, and
`enableAdminAPI: false` is what keeps it read-only. **Argo CD** can deploy
anything into the cluster, so reaching its UI is close to reaching the cluster;
it is protected by the allowlist plus its own admin password. Cloudflare Access
in front of both is the upgrade path and is not done.

## Gaps, stated plainly

These are absent, not misconfigured. Each is a decision with a reason.

| Gap | Consequence today | What closing it takes |
|---|---|---|
| **No NetworkPolicy** | any pod can reach any other pod's Service. A compromised Airflow task pod can open a socket to Trino or Polaris directly | a default-deny policy per namespace plus explicit allows. Cheap to write, needs testing against every real path — the Spark driver talks to Polaris, Airflow talks to the Spark operator's CRD, Prometheus scrapes everything |
| **No query audit log** | `eventListenerProperties: []`. Nothing records who ran which query against which table | Trino's event listener writing to S3. The `bronze.log.query_audit` namespace was created for exactly this and is currently empty |
| **No column masking or row filtering** | a gold reader reads every column and every row | same rules file as the existing access control |
| **No SSO** | a static password file; adding a person means regenerating it | OIDC against an identity provider. Needs one to exist |
| **No encryption at rest with a customer key** | S3 uses SSE-S3, RDS uses the default AWS-managed key | SSE-KMS with a customer-managed key, set at bucket and instance level |
| **Argo CD's `default` AppProject** | any Application can deploy anything anywhere | a scoped AppProject per team, restricting source repos and destination namespaces |

## Governance

### Business data

Iceberg tables are governed by the classification and lifecycle rules in
`S3_DATA_TIER.md`, which decide both the storage tier an object moves through
as it ages and whether automated deletion is permitted at all.

The classification is encoded in the namespace path itself —
`medallion.category.domain` — so `bronze.financial.invoice` and
`bronze.log.query_audit` get different retention without anyone maintaining a
separate mapping. The path IS the policy key.

### Platform data

| Data | Where | Policy |
|---|---|---|
| Polaris catalog metadata | RDS Postgres | critical state, not a log — losing it loses every table pointer. RDS automated backups and PITR, no expiry rule |
| Airflow task logs | S3 (`airflow/`) | cost-driven retention only |
| Spark event logs | S3 (`spark-events/`) | read by the History Server; cost-driven |
| Prometheus metrics | EBS, 7 days / 18GiB | both limits set, because time alone is a promise the disk cannot keep |
| EKS control-plane audit log | **disabled** | was on, reached 645 GB in CloudWatch unread, and cost more than the monitoring stack. The decision and how to reverse it are recorded in `02_eks_cluster_prod/eks-cluster.yaml` |

That last row is the honest version of an audit story: the platform HAD a
complete Kubernetes API audit trail and it was turned off, because nothing
consumed it and it was the single largest line on the bill. Turning it back on
is a decision to pay for something someone will actually read.

### Data lineage

Every bronze row carries `_ingested_at`, `_source_file` and `_run_id`. The run
ID is the SparkApplication name, which contains the processing date — so any
row in gold can be traced back through silver to the exact TLC file and the
exact job that loaded it. Details in `DATA_MODEL.md`.
