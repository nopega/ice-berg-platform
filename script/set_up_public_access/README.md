# set_up_public_access — publishing the platform to the internet

TLS certificate, Ingress rules, and DNS records for every public hostname.

This used to live inside `set_up_cluster/` as step 09, and that placement was
wrong in a way worth recording: applying the Ingress requires every backend
Service to exist — Airflow, Trino, Harbor, Grafana, Argo CD, Prometheus — so
it cannot run before `set_up_component/`. It is not cluster setup at all; it
is the act of publishing a finished platform, which is why it now sits beside
the other two phases rather than inside one of them.

## Order

```
set_up_cluster/  ->  set_up_component/  ->  set_up_public_access/
```

**With one deliberate exception:** `01_request_acm_certificate_prod.sh` talks
only to ACM and Cloudflare and can run at any point after the AWS CLI works.
It is also the longest wait in the whole project (DNS validation). Start it
early, let it validate while the components install, and the certificate is
ISSUED by the time anything needs it:

```bash
# early, right after set_up_cluster/00 and 01:
./01_request_acm_certificate_prod.sh          # guides the import, waits for ISSUED

# after ALL of set_up_component:
./02_apply_public_ingress_prod.sh             # ingress + DNS, refuses if unsafe
```

## What each script does

**`01_request_acm_certificate_prod.sh`** — the certificate.

One certificate for every hostname, because ACM certificates are immutable:
there is no API to add a name later, only a full re-request and re-validation.
The hostname list in `SAN_DOMAINS` was extended three separate times on this
project (grafana, argocd, prometheus), each costing a fresh certificate — the
comments in the script record each one as a warning to list every plausible
name up front.

The script runs the whole flow itself: request, write the Cloudflare import
file from ACM's actual response, pause for a human to import it, poll the
zone's own nameserver until the records resolve, then poll ACM until ISSUED.
Each pause and poll exists because the manual version of that step was done
wrong at least once.

**`02_apply_public_ingress_prod.sh`** — the Ingress rules and DNS.

Substitutes the certificate ARN and the source-IP allowlist into
`ingress-public.yaml` and applies it. Refuses to run if any backend Service is
missing, and refuses if Trino does not require a password — because applying
this file is the moment the platform becomes reachable from the internet.

DNS records are created **through the Cloudflare API**, not by zone-file
import. The import path failed silently three times: a file containing rows
Cloudflare considered duplicates reported errors for those and quietly dropped
the rows that were new. An API call per record either succeeds or fails with a
named reason. The token is scoped to DNS edits in one zone and stored in
Secrets Manager like every other credential here.

Every run ends with an endpoint table: each hostname fetched through the ALB
with DNS bypassed (`--resolve`, TLS still verified via SNI) next to whether
public DNS resolves it yet — so "the platform is fine, a resolver is still
caching the record's absence" is printed rather than deduced.

## Files

| File | Role |
|---|---|
| `ingress-public.yaml` | every public host rule, one shared ALB via `group.name` |
| `acm-validation-records.txt` | GENERATED by 01 — Cloudflare import for certificate validation |
| `alb-dns-records.txt` | GENERATED by 02 — kept as a record; the API path supersedes importing it |
| `.inbound-cidrs` | gitignored — the source-IP allowlist, environment-specific |

## The shared ALB

Every Ingress here carries `alb.ingress.kubernetes.io/group.name:
data-platform-public`, so the controller merges them into ONE load balancer:
one ALB (~$22/month), one certificate, six hostnames routed by host header.
The alternative — one ALB per service — would cost six times as much and need
six certificates for no benefit at this scale.

Consequence worth knowing: `load-balancer-attributes` must be
character-for-character identical on every Ingress in the group. If two
disagree, the controller refuses to build the load balancer model at all and
the NEWEST Ingress is left with no ADDRESS while the others keep working —
which reads like the new one failed on its own.

## What is deliberately NOT public

| Component | Why |
|---|---|
| Polaris management API | creates catalogs, principals and grants — port-forward only |
| Alertmanager | no auth of its own, and nothing a human needs daily |
| Argo CD *was* here too | added to the ALB later, with the trade-off recorded in ingress-public.yaml: it can deploy anything into the cluster, so its protection is the allowlist plus its own login |

The `inbound-cidrs` allowlist is the network-level control on everything here.
It is a list of source IPs, not an identity check; Cloudflare Access in front
of the sensitive hostnames is the upgrade path, and is not done.
